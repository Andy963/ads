# ADS 默认工作空间规则
## rules:
1. 数据库文件保护：未经明确许可，禁止删除或覆盖任何数据库文件。
2. 提交策略：除非用户明确要求，否则不得执行 `git commit`、`git push` 等提交操作，也不得添加 co-author。
3. 文档位置：所有新增文档必须位于 docs/ 目录内；但允许在 `.agent/skills/` 下创建/更新 `SKILL.md` 作为技能库。
4. 脚本创建：未经允许不得在项目中随意新建脚本或可执行文件；但允许在 `.agent/skills/<skill>/scripts/` 下放置与该 skill 强相关的辅助脚本（优先小而明确）。
5. 讨论阶段：方案讨论未结束或未得到批准时，禁止开始编写代码。
6. 前端构建：凡修改到前端相关代码（包含 src/frontend、前端依赖或 UI 组件），必须在交付前运行一次 `npm run build`，确保能通过编译。
7. 规划约束：多步骤任务必须先写出包含至少 2 步的计划，并在每个步骤完成后更新计划，禁止跳过或省略该流程。
8. 文档同步：任何改动导致行为、接口或流程发生变化时，必须同步更新对应的 `docs/spec/*`、README 或相关文档，保持实现与文档一致。
9. Spec 流程：默认按改动风险决定是否需要 `docs/spec/` 三件套。
   - 必须写 requirement/design/implementation：新增较完整功能、公共接口或协议变更、持久化格式变更、数据库迁移、权限/安全边界变更、调度/任务执行语义变更、跨模块行为变更。
   - 不强制写三件套：bugfix、测试修复、lint/typecheck 修复、内部重构且不改行为、文案/样式微调、已有文档补充、开发工具或脚本的小范围维护。
   - 中等风险改动可以只写短 design note 或更新既有 spec，前提是实现边界、兼容性和验证方式说清楚。
   - 如果是否需要 spec 不明确，先用一句话说明判断依据；只有高风险或影响公共行为时才暂停并请求确认。
10. Review 流程：除非用户明确要求跳过且记录原因，实施完成后必须执行 Review（通过 review workflow/技能自动化）并等待通过；Review 进行期间禁止继续修改代码或提交。
- 违反任一条即停止
